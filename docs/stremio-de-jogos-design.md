# Stremio for Games: design

Date: 2026-09-09
Status: proposal, awaiting review

## 1. Problem

Today `retro_toolbox` is a downloader. The grid shows **what the source has**: a listing of raw
files, with dump names, no reliable cover, no synopsis, no notion of a "game". If the source goes
down or changes, the grid disappears.

The goal is to invert this. The grid now shows **the console catalog**, all the games, with cover
and synopsis, and the source becomes a detail: an availability badge and a download button. A game
without a source stays on the grid, just without the button.

It is the Stremio model: a stable catalog at the center, addons plugged in around it.

## 2. Locked decisions

These decisions were made during the brainstorm and are premises of the rest of the document.

| Decision | Reason |
| --- | --- |
| **No login anywhere** | IGDB and the like require an API key and a server. Static packs per console, generated by a GitHub Action, published on GitHub Releases. The app stays offline and backendless. |
| **The grid shows everything, with an availability badge** | A game without a source appears with cover and synopsis. The catalog belongs to the console, not to the source. |
| **The app must not ship with a game origin** | A source is an addon installed by the user. No ROM URL in the binary nor in the assets. |
| **The addon is dumb** | It returns a raw listing and declares no identity. The one that guesses which game each file is is the app. |
| **Today's `consoles.json` has to become an addon** | Backward compatibility is a requirement, not a courtesy. |
| **"Where to buy" is out of scope** | There is no viable source of commercial availability for retro. |
| **OpenVGDB is included even without a license** | Explicit decision by the user. Mitigation in section 9. |

## 3. Architecture

```
   GitHub Action (monthly)                       GitHub Release
   libretro-database (DAT)      ---->            pack per console
   libretro-thumbnails (URL)                     snes.json.gz
   OpenVGDB (synopsis via CRC)                   megadrive.json.gz
                                                 ...
                                                       |
                                                       | download, local cache
                                                       v
   +---------------------------------------------------------------+
   |                            APP                                 |
   |                                                                |
   |   Metadata Pack  ----> GRID   <---- availability badge         |
   |   (2415 games)          |                    ^                 |
   |                         |                    |                 |
   |                         |              Matcher (name, tiers)    |
   |                         |                    ^                 |
   |                         v                    |                 |
   |                  game screen           raw listing             |
   |                         |                    ^                 |
   |                         |                    |                 |
   |                   SourceResolver             |                 |
   |                   "give me an HTTPS URL"     |                 |
   |                    /      |      \           |                 |
   |              Http    WebSeed    Debrid       |                 |
   |                    \      |      /           |                 |
   |                         v                    |                 |
   |            background_downloader             |                 |
   |            unzip / nsz / cia / CRC32         |                 |
   +---------------------------------------------------------------+
                              ^                    ^
                              |                    |
                        Accounts             Installed addon
                   (secure storage)          (consoles.json)
```

Four independent subsystems, each with its own spec and plan:

1. **Metadata Pack**: how the pack is built and consumed.
2. **Identity**: how a file from the source becomes a game from the pack.
3. **Addon and Accounts**: addon format, installation, credentials.
4. **SourceResolver**: how a listing item becomes a downloadable URL.

## 4. Subsystem 1: Metadata Pack

### 4.1 Sources

| Source | What it provides | License |
| --- | --- | --- |
| libretro-database, `metadat` folder | skeleton (canonical name, CRC32, MD5, SHA1, serial), genre, developer, publisher, year, franchise, ESRB | CC BY-SA 4.0 |
| libretro-thumbnails | cover URL on `raw.githubusercontent.com` | no declared license |
| OpenVGDB v29.0 | synopsis, alternate cover | no declared license |

### 4.2 Measured coverage

Measured over SNES (`Nintendo - Super Nintendo Entertainment System`, DAT v2026.08.01):

| Field | Coverage |
| --- | --- |
| Skeleton (name, hashes) | 100% |
| Genre, developer, publisher | ~90% |
| Cover, libretro-thumbnails | 86.8% |
| Cover, OpenVGDB | 75.6% |
| Cover, union of the two | **89.6%** |
| Synopsis, OpenVGDB via CRC32 join | **75.3%** (90.9% of those that join) |

Alternative tested and discarded: Wikipedia/Wikidata via SPARQL, clean CC BY-SA license, but only
**31.1%** coverage with a fuzzy join by name. No substitute.

### 4.3 Coverage per console

**24 of the 25 consoles** in the user's catalog have a DAT in libretro-database. The Wii U comes
from `metadat/no-intro/Nintendo - Wii U (Digital).dat` (3373 games), a non-obvious path. **Only the
Nintendo Switch has no pack**, and it is handled by the degradation in section 7.

### 4.4 Format and distribution

One file per console, `<console_id>.json.gz`, published on a GitHub Release with a date tag. The
app downloads on demand on the first access to the console and caches it locally.

The pack stores **a cover URL, never the image binary**. This is what resolves the licensing
problem in section 9: the app hotlinks, exactly as the browser would.

Field per game:

```json
{
  "id": "snes/crystal-vanguard",
  "title": "Crystal Vanguard",
  "dumps": [
    { "name": "Crystal Vanguard (USA)", "crc": "2D206BF7", "sha1": "...", "serial": null }
  ],
  "cover": "https://raw.githubusercontent.com/libretro-thumbnails/...",
  "synopsis": "...",
  "genre": "Role-Playing",
  "developer": "Square",
  "publisher": "Square",
  "year": 1995
}
```

The `id` is the shared public namespace, the analog of IMDb's `tt` in Stremio. It is what couples
pack, grid, favorites and local library.

Build of 2026-09-10: the SNES pack came out with 2415 games from 4268 dumps, 89.1% with a cover and
75.3% with a synopsis.

## 5. Subsystem 2: Identity

This is the highest-risk subsystem and was validated by a proof of concept before the design.

### 5.1 Two axes, not one

- **Normalized name** matches the catalog with a remote source. It is what can be done **before**
  downloading.
- **Checksum** matches the catalog with a local file. It is what can be done **after** downloading.

Confusing the two was the first mistake of the PoC and is worth recording. The first measurement
counted regional variants (USA, Europe, Rev 1, Beta 2) as ambiguity failures and reached 90.83%.
Measuring on the right axis, that of the **canonical game**, the real number is different.

### 5.2 PoC result on the correct axis

SNES, a DAT with 4268 dumps that collapse into **2415 canonical games**, against a real
archive.org listing with 4122 files:

| Tier | Files | % |
| --- | --- | --- |
| 1, exact name (rom or game) | 3685 | 89.4% |
| 2, canonical name | 343 | 8.3% |
| 3, fuzzy >= 0.90 | 26 | 0.6% |
| 4, no match | 68 | 1.6% |

- **File coverage**: 4054 / 4122 = **98.35%**
- **Game coverage**: 2342 / 2415 = **96.98%**, that is, 73 games are left without a badge

### 5.3 The silent-error floor

The measurement above is the best case: a source that mirrors No-Intro. Against non-canonical
sources, degrading 800 randomly drawn games (seed 20260909):

| Degradation | Correct | **Wrong** | Missed |
| --- | --- | --- | --- |
| GoodTools `(U) [!]` | 100% | 0% | 0% |
| Without region tag | 100% | 0% | 0% |
| Underscore in place of space | 100% | 0% | 0% |
| Article moved to the front | 78.8% | **6.1%** | 15.2% |
| Subtitle cut | 77.4% | **9.2%** | 13.4% |
| Subtitle inverted | 71.9% | **12.1%** | 16.1% |

The middle column is the problem. A wrong match is worse than no match: the user downloads a
different game and the app confidently claims it is correct. **There is a silent-error floor of
around 10% against non-canonical sources, and no name heuristic removes it.**

Design consequence: the token set tier was **removed**. It yielded +0.6% coverage and got 12% of
what it resolved wrong. A bad trade.

### 5.4 What resolves it: CRC32 over HTTP Range

A ZIP has the CRC32 of each internal file in the central directory, at the end of the file. It can
be read without downloading the ZIP:

1. `Range: bytes=-256` on the tail, find the EOCD (`PK\x05\x06`), read the offset and size of the central directory.
2. `Range` on the central directory, read the entries (`PK\x01\x02`): CRC32 at `+16`, name size at `+28`.

Measured cost: **two requests, 326 bytes, in a 3 MB ZIP.**

Tested on the 12 worst cases of the PoC, the ones no name tier resolved: **12 of 12 resolved, 4060
bytes in total.** Examples:

| Filename on the source | Real game, discovered by the CRC |
| --- | --- |
| `Velmar (Japan).zip` | `Ugorae E Ver. 2.0 - Velmar (Japan) (En,Ja).sfc` |
| `Kaseru Tsudoru Asobaru Emondo (Japan).zip` | `Emondo (Japan).sfc` |
| `Vantage - Harukoreno Azuria 2 (Japan).zip` | `Harukoreno Azuria 2 - Vantage (Japan).sfc` |
| `Kikoru Keisen Steel Jack (Japan).zip` | `Armored Patrol - Steel Jack (Japan).sfc` |

### 5.5 Final design

- The name tier resolves the majority and is free.
- Each match carries a **confidence derived from the tier**. Tier 3 is never presented as a
  certainty.
- Where the source serves a ZIP, CRC32 over Range confirms or corrects before the download.
- After the download, the CRC32 of the downloaded file is verified against the pack anyway.

### 5.6 Known limitation: disc consoles

About 11 of the 25 consoles serve `.iso`, `.bin`, `.rvz`, with no ZIP central directory. For those
the Range trick does not exist and the match falls to the name tiers, with the error floor from
section 5.3. The correct key for those systems is the **serial**, which already comes in
libretro-database. It is recorded as future work, it is not part of slice 1.

### 5.7 Third axis: the file that is already on disk

Section 5.1 speaks of two axes, but the checksum axis has two cases and only one of them was
covered. The uncovered case is the file that **already existed**: downloaded before the app
existed, copied from another machine, or brought in by another tool.

Today `library_snapshot_provider.dart` discovers what you have by scanning the directory and
indexing by exact name and by base name. That is enough while the grid shows files, because the
name on the grid is the name on disk. In PACK MODE it no longer is: the tile is a game, and saying
"you already have it" requires mapping a local file back to a canonical game, with the same error
floor from section 5.3.

Rule: **name first, CRC only when in doubt.**

1. Match by name, exact and canonical, against the pack.
2. If the name is ambiguous or does not match on any trustworthy tier, compute the CRC32 of that
   file and resolve by checksum.
3. The result is cached by `(path, size, mtime)`, so only the first scan pays, and it only pays for
   the doubtful files.

This keeps the scan cheap in the common case, which is the library the app itself downloaded and
named, and it avoids the most annoying lie possible: the tile claiming that you already have a game
that you do not have.

### 5.8 Live verification of the Range, and three limits the PoC did not record

Section 5.4 was rechecked against real sources on 2026-09-10, and the technique holds up, but with a
condition that was not written down and two pitfalls that need to become code.

**Confirmed.** Against the item `ef_nintendo_snes_no-intro_2024-04-20` from archive.org, which is
the PoC source and is still up with 4122 zips, one per game: **6 of 6 files resolved by CRC32, 2124
bytes in total, 354 bytes per file**. It matches the 326 bytes of the PoC. One of the cases shows
the value well: two files whose names differ only by an aftermarket suffix resolved to
`16 BIT XMAS 2011 - Christmas Craze (World) (Alt)` and `16 BIT XMAS 2011 - Christmas Craze (World)`,
exactly the kind of pair the name axis gets wrong silently.

**Limit 1, the CRC axis requires the ZIP to contain the ROM, not another ZIP.** The item
`snes_20250129` serves a single 2.4 GB ZIP whose 4038 entries are themselves `.zip` files. The CRC
of the central directory is the CRC of the inner zip, and the cross-check with the No-Intro DAT gave
**0 of 4038**. The rule worth writing: only use the central directory CRC when the entry name ends
in a ROM extension. Ending in `.zip` or `.7z`, the CRC is not comparable with the pack and the match
has to fall to the name axis.

In that same case the Range is still very much worthwhile, just on the other axis: **0.51 MB of
central directory return the 4038 names at once**, and they are canonical No-Intro names. One request
pays for the entire listing of a set the source does not expose any other way.

**Limit 2, the EOCD parse fails silently and expensively if it is not validated.** A request to a
Myrient `.zip` URL returned **status 200 with `Content-Type: text/html`**, a 2334-byte page.
Searching for `PK\x05\x06` on the tail matched inside the HTML and produced "28515 entries, central
directory of 779318387 bytes". Without validation the app would then emit a 779 MB Range because of
an error page. Two mandatory guards, and they are cheap: require status **206** with a
`Content-Range` header, never 200; and check `offset + size <= total size` read from the
`Content-Range` itself before the second request. Either of the two failing, the file falls to the
name axis with no second request.

**Limit 3, the real sources are heterogeneous and most do not serve the CRC axis.** Of the five SNES
items surveyed in the PoC, one is the set in 4122 zips per game, one is the 2.4 GB ZIP of zips, one
brings nine `.7z` files, one brings an `.iso` and one brings a `.rar`. Only the first serves the CRC
over Range. `.7z` and `.rar` have no central directory readable over Range, and for them the name
axis is all that exists, with the error floor from section 5.3. The slice 5 `SourceResolver` needs to
expose the shape of the item so the matcher can decide whether to try the Range or not even start.

**Useful side note.** The `archive.org/metadata/<item>` API already returns `crc32` per file for
free, with no Range at all. It is the CRC of the served file, that is of the outer ZIP, so it does
not match the pack, but it serves as a stable cache key for the match result of that file.

### 5.9 The PoC remeasured against what the app actually has

Section 5.2 measured against the DAT. The app does not have the DAT, it has the slice 1 pack, which
is the DAT after being collapsed, and the pack loses one thing on purpose: the **name of the `rom`
line**. Each dump keeps only the name of the `game` block. Before writing the matcher the
measurement was redone on 2026-09-10 with exactly the data the app will have, the same DAT and the
same listing of 4122 files from the item `ef_nintendo_snes_no-intro_2024-04-20`.

| Scenario | Tier 1 | Tier 2 | Tier 3 | No match | File | Game |
| --- | --- | --- | --- | --- | --- | --- |
| Section 5.2, with rom name | 89.40% | 8.32% | 0.63% | 1.65% | 98.35% | 96.98% |
| Without rom name, as the pack is | 86.95% | 10.77% | 0.63% | 1.65% | 98.35% | 96.98% |

**Nothing is lost, 101 files only change tier.** The `rom` name is the `game` name plus the
extension, and `norm` strips the extension, so whoever matched by rom now matches by canonical. The
coverage is identical on both ends. The practical consequence is only one: the tiers table from
section 5.2 **will not reproduce in the app**, and 86.95 / 10.77 is the right number for whoever
checks the matcher. It is not a regression.

**The builder's `canon` and the PoC's `canon` give the same result.** They are written differently:
the PoC normalizes and then strips the tags, the builder strips the tags on the raw name and
normalizes afterwards, because `norm` eats the comma that separates `Legend of Kaelis` from `The`.
Over the 4122 files the two produce the same number tier by tier. The builder stays the correct one,
because it is what generated the published `id`s, but it is recorded that the difference is
theoretical on this corpus.

**Swapping `difflib` for `rapidfuzz` in tier 3 changes nothing.** The PoC used
`SequenceMatcher.ratio`, which is Ratcliff/Obershelp; Dart has `rapidfuzz.ratio`, which is
normalized indel similarity, and the two are not the same function. With a cutoff at 0.90 the two
resolved the **same 26 files to the same 26 targets, zero divergence**. The Dart matcher can use
`rapidfuzz.ratio` with a cutoff of 90 without redoing the measurement.

**Tier 3 gets things wrong, and it can be seen with the naked eye.** Of the 26 cases, at least 4 are
wrong: `Duo Vector Recoil MK2` resolves to `duo vector recoil mk3` and `WG Cbuokdeelmu Meqazi Vol. 3`
resolves to `wg cbuokdeelmu meqazi vol 1`, two files each. That is 15% error within the tier, against
0.63% coverage gain. It is the same math that killed the token set tier in section 5.3, and it is the
concrete argument for the rule in section 5.5: **tier 3 is never presented as a certainty**. A single
digit at the end of the title is exactly what edit distance does not see.

## 6. Subsystem 3: Addon and Accounts

### 6.1 The addon is today's `consoles.json`

No field of `Console` changes. `Console.fromJson` stays intact. What exists today is already almost
the protocol:

| Already exists | Where | Stremio analog |
| --- | --- | --- |
| Installation by URL | `catalog_service.dart`, `setCatalogFromUrl` | install addon |
| Detection of two formats (List and Map) | `catalog_service.dart`, `_parseConsoles` | version tolerance |
| `list_systems` | `console_model.dart` | `addon_catalog` |
| `should_unzip`, `should_decompress_nsz`, `convert_3ds_to_cia`, `extract_contents` | `console_model.dart` | `behaviorHints` |
| `file_format`, `ignore_extension_filtering` | `console_model.dart` | `idPrefixes` |
| `regex`, `download_url`, `roms_folder` | `console_model.dart` | addon routing |

Post-processing is a property of **the source**, not of the game. This is exactly the role of
`behaviorHints` in Stremio and it is why it survives the change unaltered.

### 6.2 Accounts

The addon declares the **shape** of the authentication. Never the value.

```
addon JSON                        Settings > Accounts            secure storage
------------------------          --------------------           --------------
auth: {                    -->    [ UltraNX          ]    -->    addon:<id>/ultranx
  cookies: true                     username ______
  cookie_name: auth_token           password ______
  auth_message: "..."               [ Sign in ]
  signin: { url, params }
}
type: ia_s3                -->    [ Internet Archive ]    -->    ia/cookies
(not from an addon)        -->    [ Real-Debrid      ]    -->    debrid/realdebrid
```

The app scans all installed addons, gathers every console with `auth != null` and builds the screen.
`signinForToken` in `utils/network.dart` already implements the login flow, so the UltraNX Sign in
button is what already runs today, just in a single place.

### 6.3 Mandatory security fix

Today the token can live **inside the JSON**, which is the file the user shares. The fallback chain
in `task_queue_service.dart` is:

```dart
settings.consoleSettings[console.id]?.authToken ?? console.auth?['token'] as String? ?? ''
```

It is the same flaw as Torrentio putting the key in the URL, only in a file. In the user's real
catalog the field is empty, so nothing leaked, but the format allows it.

Two changes close the hole:

- `utils/network.dart`, `buildConsoleAuthHeaders`: `tokenOverride ?? auth['token']` becomes just
  `tokenOverride`. The value can no longer come from the file.
- `task_queue_service.dart`: the chain loses the middle term.

On installation, if the JSON comes with `auth.token` filled in, the app moves it to
`flutter_secure_storage` and clears it in the saved file. On export, it removes it.

Current state to fix: the app stores Internet Archive tokens and S3 credentials in
`shared_preferences` in plain text, without `flutter_secure_storage`. This needs to be resolved
**before** introducing a debrid key.

### 6.4 The app is already an addon server

Section 6.1 says the addon is today's `consoles.json`. This is stronger than it seemed: the **Retro
Tools Server** (`rts_server_screen.dart`) takes local folders, assembles a catalog and serves it at
`http://host:port/consoles.json`. The **New Catalog Source** tool consumes exactly that address.

```
   RTS Server              consoles.json              New Catalog Source
   local folders    ---->  http://host:port/   ---->  another app instance
   (producer)                                         (consumer)
```

The addon protocol **already exists, already runs and already closes the loop between two app
instances**. The "the addon is the `consoles.json`" decision is not a new choice, it is the
recognition of something that is already implemented on both sides.

Two design consequences:

- **Any extension of the format has to be emitted by the RTS too.** If the addon starts declaring
  `auth` or `infohash` and the RTS keeps emitting the old format, the app can no longer feed itself.
  The producer and the consumer are the same binary, so diverging is a bug with a name.
- **In PACK MODE the RTS improves for free.** Someone installs your RTS URL as an addon and, if they
  have the pack for that console, your local folder appears as a source on their grid, matched by
  name. It works with no new code because the addon is dumb and the one that guesses is the app.

The other five servers (Tinfoil, JDKV, FBI, SMB, FTP) are another category: they serve **files** to
a console or another device, not a **catalog** to the app. Nothing in this document affects them.

## 7. Grid modes

The addon does not declare a mode. The app looks at whether a pack exists for that console and
chooses:

```
                    is there a metadata pack for this console?
                              /            \
                            yes            no
                             |              |
                    PACK MODE           SOURCE MODE
        grid = pack games            grid = addon listing
        cover/synopsis = pack        cover = console.boxarts
        badge = subsystem 2 match    badge = always available
        addon only resolves download (today's behavior, untouched)
```

SOURCE MODE is the graceful degradation. **The Switch falls into it and works exactly like today.**
No regression for the only console without a pack.

## 8. Subsystem 4: SourceResolver

One interface, three implementations. Nothing above it knows what a torrent is.

```
                        SourceResolver
                   "give me an HTTPS URL"
                    /        |         \
        HttpResolver   DebridResolver   WebSeedResolver
             \             |             /
              \            |            /
               download_provider.dart, the resolveRedirects point
                        |
        background_downloader -> unzip -> nsz -> cia -> CRC32
```

The insertion point already exists: `download_provider.dart` today resolves redirects before
enqueuing, because the downloader loses auth headers on a redirect between hosts. That is exactly
where source resolution enters.

### 8.1 Listing item: one shape, three backends

```json
{ "name": "Crystal Vanguard (USA).zip", "url": "https://..." }
{ "name": "Crystal Vanguard (USA).zip", "infohash": "a1b2...", "file_index": 1234, "size": 4194304 }
```

It only swaps `url` for `infohash` plus `file_index`. **The matcher does not change a single line.**

This matters because a retro torrent is not one game per torrent, it is the whole set: a magnet with
4000 ROMs. The addon publishes the file index, which it already has because it came from the
`.torrent`, and the grid makes the distinction disappear.

### 8.2 HttpResolver

What exists today. It covers the 25 consoles of the user's real catalog: 24 point to archive.org and
1, the Switch, to `api.ultranx.ru`. It is the only resolver of phase 1 that is already written, and
extracting the interface is pure refactoring, with no behavior change.

### 8.3 DebridResolver

What Torrentio does and that we do **not** need: it is a server, so it carries a `/resolve`
endpoint, a 302 redirect instead of a proxy, a token blacklist and a circuit breaker. We are the
client and we talk to Real-Debrid directly. All of that goes away. The good idea stays: the provider
abstraction and lazy resolution, no touching debrid while the user just browses.

```
POST /torrents/addMagnet                        -> id
POST /torrents/selectFiles/{id}  { files: "1234" }   <- 4 MB of a 12 GB torrent
GET  /torrents/info/{id}         poll until status=downloaded
POST /unrestrict/link                           -> https://xxx.download.real-debrid.com/...
```

After `unrestrict/link` **there is no more torrent, there is a direct HTTPS link**, and the entire
pipeline that is already written consumes it without knowing the difference. All the post-processing
flags still apply, and the CRC32 verification against the pack too.

`selectFiles` by index is why it is worthwhile: grabbing one file from a set without downloading the
set and without seeding anything.

**Known limitation**: Real-Debrid's `/torrents/instantAvailability` endpoint is dead
(`error_code 37`). There is no way to show a reliable "cached" badge before trying. Torrentio works
around it with a collaborative cache because it renders hundreds of streams per title. We render one
game at a time, so the honest way out is to try and report the state:

```
[ Download ]  ->  resolving...  ->  RD preparing 34%  ->  downloading 78%
```

Phase 1 implements the `DebridClient` interface and only Real-Debrid. AllDebrid, TorBox and
Premiumize are left for later, with the interface ready.

### 8.4 WebSeedResolver

An archive torrent carries a web seed. Verified by opening the bencode of a real `.torrent` from
archive.org:

```
url-list : [ https://archive.org/download/
             http://ia902907.us.archive.org/7/items/
             http://ia802907.us.archive.org/7/items/ ]
```

This is BEP 19. The key lives **outside** the `info` block, so it does not affect the infohash. The
spec defines the HTTP server as a permanently unchoked seed: with zero connected peers it is
possible to satisfy 100% of the pieces by `Range` request, with per-piece SHA-1 verification for
free.

Cost: a few hundred lines, no native dependency.

Important observation: for archive.org, `url-list` resolves to the same URL the app already
downloads today. That is, **an archival-source torrent adds nothing**, and the addon should simply
point to the HTTP URL. The `WebSeedResolver` only gains value on torrents from other origins that
bring a `url-list`.

### 8.5 Native P2P is out of phase 1

Ecosystem survey on 2026-09-09:

| Option | Verdict |
| --- | --- |
| `dtorrent_task` 0.4.1, 31 stars | **no good.** No selective download by index, no web seed, and it does not parse a magnet URI, only a hex infohash. Our entire model is "one file from a set" |
| `dtorrent_task_v2` 0.5.4 | it has both things genuinely implemented, but 6 stars, one author, zero published packages depend on it, and it lists 30+ BEPs implausibly for a 10-month-old fork |
| `libtorrent_flutter`, `better_libtorrent_flutter`, `libtorrent_dart` | all three were born in 2026, all with no adoption. They download 10 to 80 MB of precompiled native binary, unsigned, from a personal GitHub Release, at build time |
| `libtorrent4j` | mature and alive, it is what LibreTorrent uses, but Java/Android. It kills cross-platform |

Blocks that do **not** exist: the Play Store policy does not mention torrent (LibreTorrent, uTorrent
and Flud are published). Apple's de facto rejection does not affect the project, which has
`android/`, `linux/`, `macos/` and `windows/` and **has no iOS**.

The block that does exist and is not technical: torrent means the user uploads. Debrid means they do
not.

Summary of the answer to "torrent without debrid": it works when the torrent has a web seed, and in
that case it is the same thing as HTTP. Without a web seed and without debrid, the honest badge is
"requires Real-Debrid". The interface above allows swapping this out later without touching the
grid, the matcher nor the pipeline.

## 9. Licensing

| Source | Situation | Treatment |
| --- | --- | --- |
| libretro-database | CC BY-SA 4.0, copyleft | The pack inherits the license and carries attribution. Published as CC BY-SA 4.0. |
| libretro-thumbnails | **No declared license.** The README says the art belongs to the publishers and credits MobyGames and Fandom | The pack stores **only the URL**. The app hotlinks. No image is redistributed. |
| OpenVGDB | **No declared license.** Frozen at v29.0, 2021-11-11 | Explicit decision by the user to use it anyway. Mitigation: the app downloads directly from OpenVGDB's own Release, instead of the pack redistributing the content. |

The risk of OpenVGDB and libretro-thumbnails is consciously accepted. It is documented here so that
the decision is traceable, not to be rediscussed.

## 10. Out of scope

- **Where to buy.** There is no source of commercial availability for retro. Confirmed with the user.
- **IGDB login.** Replaced by static packs.
- **Embedded BitTorrent client.** Section 8.5.
- **Match by serial on disc consoles.** Section 5.6.
- **AllDebrid, TorBox, Premiumize.** Interface ready, implementation later.

## 11. Risks

| Risk | Probability | Mitigation |
| --- | --- | --- |
| Silent wrong match on a non-canonical source | High, ~10% measured | CRC32 over Range where there is a ZIP, per-tier confidence in the UI, token set tier removed |
| Disc consoles without CRC over Range | Certain, ~11 of 25 | Accepted in phase 1, serial as future work |
| libretro-thumbnails or OpenVGDB go down | Medium | Hotlinked cover degrades to a placeholder, the pack keeps working |
| Real-Debrid changes the API again | Medium, it already happened with `instantAvailability` | `DebridClient` as an interface, error normalization |
| A credential leaks in a shared catalog | Already possible today | Section 6.3, mandatory before any debrid credential |

## 12. Decomposition

Each slice is its own spec and plan, in order:

1. **Metadata Pack**: GitHub Action, format, publication, download and cache in the app.
2. **Identity**: tiered matcher, CRC32 over Range, confidence in the UI, and the local axis from section 5.7.
3. **Grid and modes**: PACK MODE and SOURCE MODE, availability badge, game screen.
4. **Addon and Accounts**: accounts screen, token migration to secure storage, the section 6.3 fix, and keeping the RTS emitting the extended format per section 6.4.
5. **SourceResolver**: interface extraction, `HttpResolver` from the current code.
6. **Debrid**: `DebridClient`, Real-Debrid, listing item with `infohash`.

Slice 4, in the section 6.3 part, is a prerequisite of slice 6.
